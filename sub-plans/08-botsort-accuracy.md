# Sub-plan 8 — BoT-SORT tracking accuracy (measure, then tune)

Follows sub-plan 2 (the Dart port, done). Sub-plan 2 proved the Dart port **matches the Python
reference**: 4 synthetic parity fixtures in `test/tracking/fixtures/`, generated by
`tracking-validation/notebooks/generate_reference_fixtures.ipynb`. It never measured whether the
tracker **tracks coral well**. This sub-plan is about that second question.

**Goal (decided 2026-09-28): tracking accuracy**, meaning fewer ID switches, fewer fragmented tracks,
and above all fewer **double-counted colonies**. Unique track IDs are what the post-transect density
and size-frequency metrics count (sub-plan 4), so a tracker error here is a survey-result error.
Runtime speed is out of scope: the tracker is cheap next to per-detection classification in the live
loop.

The Specification's Phase E requires reporting **MOTA, MOTP, IDF1, and Track Continuity**, framed
against Ouassine et al.'s 82.63% MOTA, which was measured with a fixed camera. None of those numbers
exist yet, because the project has no tracking ground truth. **Measuring comes first. Tuning without a
measurement is guessing.**

## What's wrong or unknown today (verified 2026-09-28)

1. **Camera motion compensation (CMC) is built but switched off in the app.** `CameraMotionCompensator`
   is ported and unit-tested (`test/tracking/camera_motion_compensation_test.dart`,
   `bot_sort_tracker_cmc_test.dart`). But `live_transect_screen.dart` constructs `BoTSortTracker()` with
   no compensator and never passes a `frame` to `update`, so the live app runs the equivalent of
   `cmc_method='none'`. The camera is handheld by a swimming diver, so every colony moves in image
   space every frame. That's exactly the case CMC exists for, and the most likely single biggest gain.
2. **The thresholds are the reference's pedestrian (MOT17) defaults, never tuned for coral:**
   `trackHighThresh 0.6`, `trackLowThresh 0.1`, `newTrackThresh 0.7`, `matchThresh 0.8`,
   `trackBuffer 30`.
   - **Spawning:** if `coralvos_primary`'s confidence for real colonies often sits below 0.7, those
     colonies never spawn a track at all (undercounting).
   - **Units:** `trackBuffer` is in **tracker updates, not seconds**. The live stream runs inference at
     8 Hz (`inferenceFrequency: 8`), so 30 updates is **~3.75 s** of lost-track memory, not the ~1 s
     it means on 30 fps MOT17 video.
   - **Status:** nobody has chosen these values for this domain.
3. **Every track counts toward the total, however brief.** A detection that flickers for one or two
   frames becomes a track ID, is persisted by `_finalizeSession()`, and counts toward density.
4. **No real-video tracking evaluation exists.** Four synthetic fixtures verify parity, not quality.
5. **`_removedStracks` grows without bound** over a 10-20 minute transect. The Python reference does
   the same. That doesn't change results, but memory use and the per-frame `subTracks` cost grow with
   transect length.

## Ground truth: pseudo-tracks derived from CoralVOS

No dataset in the repo has per-colony track IDs. **CoralVOS** (`machine-learning-pipeline/datasets/
coralvos/`) is the only real dive/transect video source: 125 videos, ~360-390 frames each, plus
per-frame masks. Those masks are **binary coral vs background with no instance IDs** (confirmed by a
full pixel scan, `sub-plans/track1-handoff.md`). So the ground truth has to be derived, and its
limitations stated honestly in the thesis:

- **Instances:** per-frame connected components of the binary mask. This is the same method
  `18_stage_b_coralvos_primary.ipynb` already uses for training pseudo-instances. Each component
  becomes a ground-truth box.
- **Identity:** components are linked frame to frame by **mask IoU** between consecutive annotated
  frames. Linking on perfect masks is far easier than tracking noisy detections, which is why it's
  usable as ground truth, but it isn't free:
  - **Merge/split events** (two colonies' components touching, or one splitting under perspective) have
    no correct identity. Mark those components and frames as **ignore regions**: neither matches nor
    false positives count there, as MOT17 does for ambiguous areas. Every colony that stays a single
    component is scored normally.
  - **Verify the linking by eye** before trusting it. Render a contact sheet of linked IDs overlaid on
    sampled frames for every evaluation video, following this project's standing verify-don't-assume
    discipline (e.g. `19_coralvos_split_and_quality_audit.ipynb`).
- **Which videos:** only the **13 reserved CoralVOS videos** (`i % 10 == 0` by sorted name, pHash-
  checked independent). `coralvos_primary` never trained on them, so the detections fed to the tracker
  are honest. Split those 13 **by video** into a **tuning set (6)** and a **held-out test set (7)**.
  Choose parameters on tuning, then report once on test. Never tune on test.
- **Partial masks:** some videos' masks stop before the video ends (e.g. `video123`). Evaluate only the
  masked span, the same rule as `20_coralvos_coverage_benchmark.ipynb`.
- **Frame rate: verify, don't assume.** CoralVOS ships JPEG frames (first frame `00016.jpg`, so possibly
  strided) with no frame-rate metadata. Find the source frame rate and any extraction stride (arXiv:
  2310.01946 or the dataset site). Then subsample frames so the tracker sees roughly the app's **8
  updates/second**. If the rate can't be established, report results at 2-3 plausible rates rather
  than one guessed one.

## Evaluation harness

It's split along this repo's rule: Python lives in notebooks, and Claude doesn't run Python; Dart
can run.

1. **Notebook `tracking-validation/notebooks/01_coralvos_tracking_groundtruth.ipynb`** builds the
   pseudo ground truth in MOTChallenge format (`frame,id,x,y,w,h,conf,class,visibility`), with ignore
   regions and a linking contact sheet. It follows the run-versioned logging convention
   (`runs_tracking/<RUN_ID>/`, `latest_run.txt`).
2. **Notebook `…/02_coralvos_detections.ipynb`** runs `coralvos_primary` (same weights as the shipped
   Core ML asset, resolved through its `latest_run.txt`) over the subsampled frames. It writes per-frame
   detections (box, score) to JSON. That way the tracker is always tuned on the **real model's** score
   distribution, which is what threshold tuning is about.
3. **Dart tool `mobile/tool/track_eval.dart`** (`dart run`) feeds those detections, plus grayscale
   frames loaded via `opencv_dart` when CMC is on, through the **actual Dart `BoTSortTracker`** and
   writes MOT-format tracker output. It evaluates the code that ships, not the Python reference, and
   can run parameter sweeps headlessly.
4. **Notebook `…/03_tracking_metrics.ipynb`** scores tracker output against the ground truth with
   **TrackEval**. It reports:
   - HOTA, MOTA, MOTP, IDF1, ID switches, fragmentations, and Track Continuity (the Specification's
     set).
   - A **count error**: unique confirmed track IDs vs ground-truth colony count, per video. This is the
     project's most decision-relevant number, since it feeds density directly.
5. **An oracle run as a diagnostic:** feed the tracker the **ground-truth boxes** instead of model
   detections. This separates tracker error from detector error. If tracking is good on the oracle but
   poor on real detections, the problem is Stage B, not BoT-SORT, and tuning the tracker can't fix it.

## Steps

### 1. Baseline
Build the harness above. Score the tracker **as shipped today** (MOT17 defaults, CMC off) on the tuning
and test sets, plus the oracle run. Record the result. It's the number every later change is compared
against.

### 2. Camera motion compensation
- Offline first: CMC on vs off in `track_eval.dart`, same defaults. Keep CMC only if it measurably
  improves IDF1, count error, or ID switches on the tuning set.
- If it helps, wire it into `live_transect_screen.dart`:
  - Construct the tracker with a `CameraMotionCompensator`.
  - Pass a downscaled `GrayscaleFrame` built from the streaming payload's `originalImage` (already
    delivered each frame for crop-classify).
- Measure the added per-frame latency on-device when hardware allows. If it breaks the Spec's 5-8 fps
  budget, run CMC on a smaller downscale.
- This is a deliberate pipeline change. It's outside sub-plan 6's presentation-only rule and belongs
  here.

### 3. Threshold tuning for coral at 8 Hz
- First, plot `coralvos_primary`'s detection-score distribution on the tuning set: true matches vs
  false positives, against ground truth. That's where sensible `trackHighThresh` and `newTrackThresh`
  values come from, instead of a blind grid.
- Then run a bounded sweep on the tuning set with `track_eval.dart`:
  - `trackHighThresh`, `trackLowThresh`, `newTrackThresh`
  - `matchThresh`
  - `trackBuffer`, expressed as **seconds × 8 Hz**
- Pick by IDF1, with count error as the tie-breaker. Keep the sweep small, and log every arm, so the
  choice is explainable in the thesis and not overfit to 6 videos.
- Make `trackBuffer` explicit about units: express it in seconds and convert using the inference
  frequency, so a later fps change can't silently change its meaning.

### 4. Minimum-track-length filter for counting
- A track counts as a colony only if it stayed confirmed for at least **N tracker updates**. N is
  chosen on the tuning set by count error.
- This is applied where colonies are **counted and persisted** (the live tally and `_finalizeSession()`
  filtering), not inside `BoTSortTracker`. That keeps the tracker bit-identical to the reference, so
  parity tests stay valid.
- Short tracks are still logged for diagnostics, just not counted.

### 5. Hygiene: bounded `_removedStracks`
Drop removed tracks once they're older than `trackBuffer` frames. They can no longer affect
`lostStracks` because those are aged out on the same horizon. Prove the output is unchanged: all 4
parity fixtures pass, and a long synthetic sequence gives identical output before and after.

### 6. Only if steps 2-4 fall short: mask-IoU matching (experimental)
- Box IoU is a poor match for irregular, blobby colony shapes. Mask IoU uses the per-instance masks
  the pipeline already carries in `payload`.
- This is a **deviation from BoT-SORT**. Build it as a separately named option (default off), evaluate
  it on the tuning set, and document it as a project-specific change if kept, in the same way the Dev
  Plan labels engineering decisions.
- Don't start it unless the earlier steps leave a clear gap.

### 7. Report
- Run the held-out test set **once** with the final configuration, and report baseline vs final side by
  side, oracle included.
- Write `docs/botsort-tracking-accuracy-on-coralvos.md`, per root `CLAUDE.md`'s documentation rule. It
  covers:
  - the pseudo-ground-truth method and its limits
  - the tuning/test split
  - every arm tried
  - the final numbers framed against Ouassine et al. (fixed camera vs handheld, per the Spec)
- Update the Specification's Phase C "Tracking" entry with the chosen parameters and whether CMC is on.

## Rules
- **Parity is preserved.** The 4 existing fixtures must keep passing. Anything that changes tracker
  semantics is either a parameter (steps 2-3) or lives outside `BoTSortTracker` (step 4), except
  explicitly labelled deviations (step 6).
- **No Re-ID / appearance features.** That exclusion is settled (Spec Phase C, Dev Plan Track 2) and
  isn't reopened by this sub-plan.
- **Held-out means held out.** Each configuration is scored on test only after it's chosen.

## Done when
- MOTA, MOTP, IDF1, Track Continuity, and count error exist for the shipped tracker on 7 held-out
  CoralVOS videos, baseline vs tuned, with an oracle-detection comparison. The pseudo-ground-truth
  method is documented and its linking was visually verified.
- CMC is either enabled in the live app with measured benefit, or deliberately left off with the
  measurement that justified it.
- Tracker parameters are chosen from coral data at the app's real update rate, and the counting filter
  is in place. The existing parity and tracking tests pass.
- `docs/botsort-tracking-accuracy-on-coralvos.md` exists and the Specification is updated.

## Caveats to state in the thesis
- The ground truth is **derived from binary VOS masks**, not hand-labelled tracks. Touching colonies are
  excluded via ignore regions, so the scores describe tracking of separable colonies, which is also the
  case the Spec targets ("sparse, non-overlapping colonies").
- CoralVOS isn't Cordova footage. A Cordova test clip with hand-labelled IDs would be the real field
  validation, and doesn't exist yet (`track1-handoff.md`, "Do these first" #5).
